## Changes

ContextTrace v0.1.17 brings the unreleased v0.1.16 fixes together with Linux and macOS development work and repository maintenance.

- Improve prompt reconstruction and Claude multi-tool accounting, reject cyclic ancestry, and keep incomplete usage unpriced.
- Protect acknowledged archive revisions during failed writes, redact JSON credential values, and keep live observation working when alerts are disabled.
- Restrict direct file opening to supported data files, bound instruction-file reads, preserve notification identity across agents, and keep sessions browsable when usage data is missing.
- Add Linux desktop development and packaging support and macOS port and build preparation. Published release assets remain Windows x64 only; Linux assets have not been published, and native macOS compilation, launch and installation remain unverified.
- Simplify content hashing and repository maintenance, and keep release packaging and publication in Woodpecker.

See the [v0.1.16 notes](https://github.com/aneskurtovic/ContextTrace/blob/main/docs/releases/v0.1.16.md) for details of the included fixes.

## Remaining limits

Context membership depends on recorded evidence; exact Codex request identity and aggregated Claude request iterations remain capture limitations. General archive orphan reconciliation remains open. The instruction reader is not race-proof against concurrent ancestor replacement and does not determine Unix mount locality. File-extension policy does not verify the associated Windows reader. Legacy notification tombstones without retained records cannot be attributed reliably; persisted session cursors continue to govern replay. Parser compatibility is scoped to the [fixture catalog and policy](https://github.com/aneskurtovic/ContextTrace/blob/main/docs/FORMAT-COMPATIBILITY.md).

Separate clean-host installer and updater acceptance, native desktop visual and interaction checks, Windows toast and file-association behavior, and real-agent resume remain unverified. Release publication and asset checks are performed in the Woodpecker Windows tag pipeline; those checks do not replace clean-host acceptance.
